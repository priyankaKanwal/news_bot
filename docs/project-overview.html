At a glance

News sources are configured in feeds.yaml. A manual ingestion command fetches their RSS entries, cleans and filters the articles, then saves overlapping text chunks and metadata in Qdrant. The web app sends a question to FastAPI; the RAG layer searches those chunks, optionally reranks them, and asks Ollama to write a concise answer using only the selected articles. PostgreSQL stores conversations and message history.

Grounded, not all-knowing: answers depend on indexed articles in the configured feeds. The assistant is instructed to say when the retrieved evidence is insufficient; it is not a general-purpose or live web search engine.

What the app does

Collects configured news

Reads RSS feeds for publishers such as BBC News, The Hindu, Times of India, Hacker News, and NDTV.

Finds related stories

Uses semantic vector search and a cross-encoder reranker to select chunks related to the user's question.

Answers with evidence

Generates concise answers from retrieved article text and returns source titles, publishers, dates, links, and scores.

Supports headline roundups

Recognizes broad “latest/news/today” questions and can use newest articles, optionally filtered by category or publisher.

Saves chat history

Creates conversations, restores messages and sources, lists recent chats, and allows a conversation to be deleted.

Keeps an article window

Ingestion and retrieval are limited to articles published within the last 30 days; old vectors are removed on ingestion.

Architecture

The app has two paths: a batch-style ingestion path that prepares searchable news, and an interactive chat path.

RSS feeds → Python ingestion → clean / filter / deduplicate → chunk + embed → Qdrant
                                                                      ↑
React + Vite → HTTP → FastAPI → retrieve / rerank → Ollama → answer + sources
                         └──────────────────────────────→ PostgreSQL chat history

Qdrant is the article knowledge base. PostgreSQL is the relational store for conversations and messages; it is not the vector-search database. Models and chat generation run locally through Hugging Face sentence-transformers and Ollama.

Article ingestion: source to searchable index

Run python -m ingestion.ingestion_service from the repository root for a one-off refresh, or python -m ingestion.scheduler to start the standalone daily scheduler.

Load feedsValidate feed names, categories, and HTTP/HTTPS URLs from YAML.
Fetch RSSRequest and parse entries; transient request failures are retried, and a failed feed is reported without stopping other feeds.
Normalize + cleanMap publisher-specific fields into one shape; strip HTML, normalize text, parse dates, and canonicalize URLs.
Filter + deduplicateKeep recent valid articles; skip repeats by stable article ID, URL, publisher-scoped GUID, or normalized text.
Chunk + indexSplit text into 500-character chunks with 100-character overlap, attach article metadata, embed, and store in Qdrant.

The ingestion report includes per-feed counts and errors, duplicates removed, expired chunks deleted, and the number of new articles and chunks stored. Stable URL-based article IDs and chunk IDs help repeated runs avoid re-indexing existing articles.

The standalone scheduler runs daily at 02:00 UTC by default. Configure INGESTION_SCHEDULE_HOUR, INGESTION_SCHEDULE_MINUTE, and INGESTION_TIMEZONE in the root .env file to change the time. Keep the scheduler process running; it is separate from the FastAPI server and does not run ingestion immediately on startup.

Question to answer: request lifecycle

  1. The React interface sends a question (3–500 characters) and, for an existing chat, its conversation UUID to POST /api/chat.
  2. FastAPI validates the payload and saves the user's message in PostgreSQL; a new conversation title is based on the question.
  3. The chat service searches Qdrant for recent passages using the local bge-small-en-v1.5 embeddings and a relevance threshold.
  4. When enabled, bge-reranker-base reorders candidate passages; the best configured number are included as context. Broad news questions can instead use a newest-article browse path.
  5. LangChain sends the question and selected article context to the configured Ollama model. The prompt requires source-grounded facts and a fixed “not enough information” response when evidence is missing.
  6. The API groups chunks by article, returns the answer and source metadata, then saves the assistant's message and sources in PostgreSQL.
  7. The UI displays the answer and clickable HTTP(S) article links. Saved chats can be reopened or deleted.

Chat generation is synchronous in the endpoint; FastAPI executes blocking work in its thread pool. Responses are not streamed.

Data and API surface

Qdrant: article knowledge

Collection news_articles contains vectorized chunks and payload metadata such as article ID, title, publisher, category, canonical URL, and publication timestamp.

PostgreSQL: chat history

conversations stores chat titles and timestamps. chat_messages stores role, content, timestamps, and source metadata as JSON.

Run the project locally

Prerequisites: Python 3.11, Node.js/npm, Docker Compose, and Ollama with the configured model available.

  1. Install Python packages from requirements.txt and frontend packages with npm ci in frontend.
  2. Set up a root .env for PostgreSQL, Qdrant, and Ollama. The local Compose defaults are for development only.
  3. Start the data services with docker compose up -d, and start Ollama.
  4. Run article indexing from the repository root:
python -m ingestion.ingestion_service

In separate terminals, start the API and frontend:

python -m uvicorn backend.main:app --reload
cd frontend
npm run dev

The frontend defaults to http://localhost:8000 for the API, and Vite normally serves it at http://localhost:5173.

Current scope and trade-offs

  • Feed refresh happens only when the ingestion command is run; automatic scheduling is not built in.
  • Answers are not streamed; a request waits for retrieval and local LLM generation to finish.
  • Only the configured RSS sources and ingested recent articles are searchable. Full article text is not separately crawled from publisher websites.
  • The frontend CORS allowlist currently targets http://localhost:5173; conversation ownership/authentication is not implemented.
  • Local embedding and reranking models may need to download on first use and require sufficient memory/storage.
  • The Compose credentials are development defaults. The current API is intended for local development, not public exposure without access control and production hardening.
