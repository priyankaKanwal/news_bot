AI-Powered News Intelligence Chatbot

Start here

The whole project in plain English

Forget the AI words for a minute. Picture a small office with a clippings room and two staff members.

The night clerk comes in every morning. They collect the newest articles from a list of news websites, cut away the ads and clutter, and throw out any copy of a story already on file. Then they file each article. They don't file alphabetically, though. They file by what the article is about, so all the interest-rate stories sit on one shelf and all the cricket stories on another. Before leaving, they throw away any clipping more than 30 days old.

The researcher sits at the front desk. When a visitor asks "What did the RBI announce recently?", the researcher walks to the shelf that matches that topic and pulls the eight closest clippings. They hand those to a very fast writer with one strict instruction: "Write an answer using only these clippings, and say which clipping each fact came from. If they don't cover it, say you don't know."

That's the whole project. The night clerk is your ingestion pipeline. The shelves are the vector database. The researcher is your backend API. The fast writer is the LLM (a model like Gemini or ChatGPT). The front desk is your React chat page.

Why not just ask ChatGPT or Gemini directly? On their own, these models only know what they read during training, which ends months before today. They don't know this morning's news, and when they don't know something they often write a confident, made-up answer. This project gives the model fresh clippings and forbids it from going beyond them. That method has a name: RAG, short for Retrieval-Augmented Generation, which means "look things up first (retrieval), then write (generation)".

The one new idea: filing by meaning

A computer can't tell that "RBI hikes repo rate" and "central bank raises borrowing costs" say the same thing. Searching for the word "RBI" would miss the second headline. So we use an embedding model: a ready-made service that reads a piece of text and gives back a list of numbers, like GPS coordinates on a map of topics. Texts about similar things get coordinates close together, even when they share no words.

The real map has hundreds of dimensions instead of two, but the idea is the same as this picture. Your question gets coordinates too, and "search" just means finding the clippings closest to it.

What happens to one article

  1. The clerk reads a news site's RSS feed, a plain list of its latest headlines that sites publish for programs to read.Found: "RBI keeps repo rate unchanged", 4 Nov, The Hindu
  2. Strip HTML tags and junk; convert the date to one standard time zone.
  3. Check the database: have we stored this link before? If yes, skip it.
  4. Cut a long article into short passages called chunks, a few paragraphs each.
  5. Send each chunk to the embedding model and get its coordinates back.[0.013, −0.27, 0.88, … ] (768 numbers)
  6. Save the coordinates plus the headline, link, publisher and date in Qdrant.
  7. 31 days later, the cleanup job deletes it.

What happens to one question

  1. The visitor types a question in the chat page."What did the RBI announce recently?"
  2. Your backend sends the question to the same embedding model and gets its coordinates.
  3. Ask Qdrant: "the 8 nearest chunks, published in the last 30 days only".
  4. If nothing is close enough, reply "I don't have recent news on that" and stop.
  5. Otherwise, send the chunks plus strict instructions to the LLM.
  6. The answer appears word by word, like ChatGPT does (streaming), with numbered links to the original articles."The RBI kept the repo rate at … [1]" → [1] The Hindu, 4 Nov

What RAG adds

The big picture

Two programs that share a database

The PRD lists seven modules, but there are really two independent programs. Seeing them separately is the most useful thing you can do before writing code.

The ingestion pipeline (Modules 1–5)

A background job. Nobody talks to it. Once a day it fetches feeds, cleans articles, drops duplicates, turns text into vectors, stores them, and deletes anything older than 30 days.

Think of it as a nightly ETL batch job, like a Spring @Scheduled task or a node-cron script.

The chat app (Modules 6–7)

A normal web app. A React UI calls a FastAPI endpoint, which searches the vector DB, sends the hits to an LLM, and streams an answer with source links back.

Think of it as a REST API with one smart endpoint, plus a chat UI you already know how to build.

Why this matters. The PRD's scalability section says to avoid coupling ingestion with the chatbot. If they only share Qdrant (and Postgres), you can build, test and demo each half on its own. You'll start with a tiny version of both halves, then grow them one version at a time (see "Build it in versions").

Architecture

How data moves through the system

Concepts to learn

Five ideas the whole project rests on

You'll be asked to explain these in the demo (5% of the marks is "understanding of architecture"). Learn them before writing the RAG code.

Embedding

A model turns text into a fixed-length list of floats, for example 768 numbers. Texts with similar meaning produce vectors that sit close together.

Like a hash function, except similar inputs land near each other instead of far apart.

Vector database

Stores vectors and finds the nearest ones to a query vector quickly. Each vector carries a JSON payload you can filter on.

Like a table whose index answers "most similar" instead of "equal to". Payload filters work like a WHERE clause.

Chunking

Long articles are split into pieces of a few hundred words with a little overlap. Each chunk becomes its own point, with the parent article's metadata copied onto it.

Why: one vector for a 2,000-word article blurs its meaning; smaller chunks match questions more precisely.

RAG

Retrieval-Augmented Generation: search first, then give the LLM the found text and tell it to answer only from that. The LLM writes; your database supplies the facts.

Like an open-book exam where the model may only quote the pages you handed it.

Metadata filtering

Restricting a vector search by payload fields, here published_at. Qdrant applies the filter during the search, so you still get the top-k results inside the window.

Store dates as integers (Unix seconds) so range filters like ≥ and < work.

Grounding

Every claim in an answer should trace to a retrieved chunk. If the search finds nothing relevant, say so instead of letting the LLM guess.

Practical check: if the best similarity score is below a threshold, skip the LLM and return "not enough information".

Data model

What gets stored, and where

Qdrant point (one per chunk)

id:      uuid5(article_id, chunk_index)
vector:  [0.013, -0.27, ...]   # e.g. 768 floats
payload: {
  "article_id":   "sha256 of normalized URL",
  "chunk_index":  0,
  "title":        "...",
  "content":      "chunk text",
  "publisher":    "The Hindu",
  "category":     "Business",
  "article_url":  "https://...",
  "published_at": 1762300800,   # int, UTC
  "ingested_at":  1762387200
}

Every chunk carries published_at, so one delete-by-filter removes all of an article's chunks at once, as Module 5 requires.

Postgres tables

articles(
  article_id PK, url UNIQUE, guid,
  content_hash, title, publisher,
  published_at, ingested_at,
  chunk_count, status
)
ingest_runs(
  id, started_at, finished_at,
  feed, fetched, new, skipped,
  failed, error
)
cleanup_runs(id, ran_at, cutoff, deleted)
chats(id, created_at, title)
messages(id, chat_id, role,
         content, sources_json)

The articles table gives a fast "have I seen this?" check before any embedding is paid for. The run tables are your ingestion and cleanup logs.

Dedup level 1: URL

Normalize the URL (lowercase host, drop utm_* and fragments), hash it, look it up. Catches the same story fetched twice.

Dedup level 2: GUID and content hash

Compare the feed's GUID and a hash of the cleaned title + description. Catches the same article at a slightly different URL.

Dedup level 3: similarity

After embedding, search Qdrant for a very close match (cosine above about 0.95) from the last few days. Catches syndicated copies across publishers.

How a question is answered

The chat endpoint, step by step

Retrieve with the date filter

from qdrant_client import models

cutoff = retention_cutoff(now_utc())  # one shared function
hits = qdrant.query_points(
    collection_name="news_chunks",
    query=embed(question),
    limit=8,
    query_filter=models.Filter(must=[
        models.FieldCondition(
            key="published_at",
            range=models.Range(gte=int(cutoff.timestamp())),
        )
    ]),
    with_payload=True,
).points

if not hits or hits[0].score < MIN_SCORE:
    return NO_INFO_ANSWER

Prompt the LLM to stay grounded

SYSTEM = """You are a news assistant.
Answer ONLY from the numbered sources below.
Cite sources as [1], [2] after each claim.
Mention publication dates when relevant.
If the sources do not answer the question,
say you don't have enough recent news on it.
Never invent events, numbers or quotes."""

context = "\n\n".join(
  f"[{i}] {h.payload['title']} "
  f"({h.payload['publisher']}, {date(h)})\n"
  f"{h.payload['content']}"
  for i, h in enumerate(hits, 1))

Streaming and sources

Return a StreamingResponse using Server-Sent Events. Send the sources list first as one event, then the answer tokens, so the UI can render source cards right away.

Create a payload index on published_at (type integer) when you create the collection, so date filtering stays fast as the collection grows.

For follow-up questions, rewrite the latest question into a standalone one using the last few messages before embedding it.

v0 in full: the whole RAG idea in one file

Three fake news items, no database, no web server. Run it, read the similarity scores it prints, then try the experiments below the code.

# rag_v0.py: the whole RAG idea in about 40 lines
# Setup:  pip install google-genai numpy
#         set the GEMINI_API_KEY environment variable (from Google AI Studio)
import numpy as np
from google import genai

client = genai.Client()                  # reads GEMINI_API_KEY
EMBED_MODEL = "gemini-embedding-001"     # check current model names in Google AI Studio
CHAT_MODEL = "gemini-2.5-flash"

# 1. Our "database": a few sample news items
news = [
    {"title": "Sample: Central bank keeps interest rate unchanged", "url": "https://example.com/1",
     "text": "The central bank held its key lending rate steady, saying inflation is easing."},
    {"title": "Sample: Chipmaker announces new AI processor", "url": "https://example.com/2",
     "text": "A chip company unveiled a processor designed for training AI models."},
    {"title": "Sample: India wins the cricket series 3-1", "url": "https://example.com/3",
     "text": "India won the final match by six wickets to take the series."},
]

def embed(texts):
    """Turn a list of texts into a list of number-lists (vectors)."""
    result = client.models.embed_content(model=EMBED_MODEL, contents=texts)
    return [np.array(e.values) for e in result.embeddings]

def similarity(a, b):
    """Cosine similarity: close to 1 means 'about the same thing'."""
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))

# 2. "Ingestion": turn every article into numbers, once
news_vectors = embed([n["title"] + ". " + n["text"] for n in news])

# 3. "Retrieval": score every article against the question
question = "What did the central bank decide about rates?"
q_vec = embed([question])[0]
scored = sorted(
    ((similarity(q_vec, v), n) for n, v in zip(news, news_vectors)),
    key=lambda pair: pair[0], reverse=True,
)
for score, n in scored:
    print(f"{score:.3f}  {n['title']}")      # look at these numbers!
top = [n for score, n in scored[:2]]

# 4. "Generation": hand the clippings to the LLM with strict rules
clippings = "\n".join(f"[{i}] {n['title']}: {n['text']} ({n['url']})"
                      for i, n in enumerate(top, 1))
prompt = f"""Answer using ONLY the numbered news below. Cite sources like [1].
If the news does not answer the question, say you don't have that information.

{clippings}

Question: {question}"""

answer = client.models.generate_content(model=CHAT_MODEL, contents=prompt)
print("\n" + answer.text)

Experiments that teach you RAG:

  • Ask about cricket. Watch the scores reorder.
  • Ask "Will it rain tomorrow?" The scores are all low and the answer should be "I don't have that information". That's the PRD's test 10.
  • Delete the "ONLY" rule from the prompt and ask about something not in the list. See the LLM make things up. That's why the rule exists.
  • Ask using different words ("Did borrowing costs change?"). It still finds the central bank item, which keyword search wouldn't.

Pitfalls

Mistakes that cost marks

Relying on cleanup alone for the 30-day rule.

Between cleanup runs, old articles can still be retrieved. Always filter at search time too.

Storing dates as strings or in local time.

Range filters need numbers. Convert everything to UTC Unix seconds at ingestion.

Using ingestion date where the PRD wants publication date.

An article published 40 days ago but fetched today must still be excluded. Keep both fields.

Deleting the article row but leaving its chunks.

Copy published_at onto every chunk and delete by filter, not by a list of parent IDs.

Embedding before checking for duplicates.

Do the cheap URL and hash checks first; embedding calls cost time and quota.

Changing the embedding model mid-project.

Vectors from different models can't be compared. Re-create the collection and re-ingest if you switch.

Putting the API key in the React app.

Anything in frontend code is public. The browser only ever talks to your FastAPI backend.

Pasting AI-generated code you can't explain.

The PRD says you'll be asked about every component. Write each module yourself, test it alone, then integrate.
